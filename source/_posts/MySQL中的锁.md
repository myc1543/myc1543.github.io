数据库锁设计的初衷是处理并发问题。

根据加锁的范围，MySQL里的锁大致分为`全局锁` `表级锁` `行锁`三类。



## 1. 全局锁

全局锁是对整个数据库实例加读锁，使得数据库处于只读状态，数据库的其他操作(数据更新语句、数据定义语句和更新类事务的提交)都会被阻塞。

```
flush tables with read lock;
```



### 1.1 使用场景

全局锁的典型使用场景是：做全库逻辑备份。

```
// 加全局锁
flush tables with read lock;

// 数据备份
mysqldump -uroot –p1234 itcast > itcast.sql

// 释放锁
unlock tables;
```



**为什么在数据备份时需要加全局锁？**

假设现在有一张订单表和库存表。业务执行下单操作，先扣减库存，然后生成订单。

```

1.备份库存表
2.下单
3.备份订单表
```

如果对每个表分别做备份，以上面这个备份时机为例，此时备份的数据是库存没有减少，但是有对应的订单，出现了数据不一致的情况。

如果加上全局锁，所有更新操作都会被阻塞，直到备份完毕，此时备份的数据就是完整的。

### 1.2 全局锁的影响

锁主库，主库在锁期间都不能执行更新， 业务基本停摆

锁从库，从库在锁期间不能执行主库同步过来的binlog，会导致主从延迟。



## 2.表级锁

表级`锁的粒度是表，在MySQL中，主要有两种表级锁：`表锁`和`元数据锁


### 2.1 表锁

```
// 加锁
lock tables ... read/write
// 解锁
unlock tables 
```

客户端断开时也会自动释放表锁。

表锁除了会限制其他别的线程读写外，也会限定本线程接下来操作的对象。

```\
// 线程A 加锁
lock tables t1 read, t2 write;
```

其他线程写t1，读写t2的语句都会被阻塞。同时线程A在解锁之前，只能执行读t1，读写t2的操作。



### 2.2 元数据锁MDL(metadata lock)

MDL不需要显式使用，在访问一个表的时候会自动加上。MDL的作用是保证读写的正确性，避免因为表数据变更二导致数据错误。

当对一个表做增删改查时，加MDL读锁。当对表结构做变更时，加MDL写锁。

- 读锁之间不互斥，所以可多线程对一张表做增删改查
- 读写锁、写锁之间互斥，保证变更表结构操作的安全性。



### 2.3 MDL的影响

```
sessionA：查表
sessionB：查表
sessionC：更改表结构 （阻塞）
sessionD：查表 （阻塞）
```

sessionA和sessionB加MDL读锁，不会相互阻塞，可以正常执行，sessionC加MDL写锁，被阻塞。如果后续有增删改查操作，都会被阻塞住。

如果客户端有重试机制，这个库的线程很快会爆满。

### 2.4 安全改表

首先，需要解决的是长事务，在做DDL变更时，考虑暂停或者kill长事务。

如果是读写操作较多的热点表，比较理想的机制是在改表语句里面设定等待时间，如果在等待时间里拿到MDL写锁最好，如果拿不到也不会阻塞后续的业务语句。之后再重试给改表语句。



### 2.5 意向锁

在InnoDB中，由于行锁的存在，表锁与行锁之间也会存在冲突，为了减小行锁与表锁的冲突，设计意向锁来解决这个问题。

在加行锁之前，会先在操作表上加意向锁，如果有其他线程需要加表锁，就会先去判断是否有意向锁，而不用查找每行的行锁。

- 意向共享锁（IS）：由语句select ... lock in share mode添加，与表锁共享锁（read）兼容，与表锁排他锁（write）互斥。在准备给表数据添加一个S锁时，需要先获得该表的IS锁
- 意向排他锁（IX）：由insert、update、delete、select...for update添加 。与表锁共享锁(read)及排他锁(write)都互斥，意向锁之间不会互斥。在准备给表数据添加一个X锁时，需要先获得该表的IX锁

## 3. 行锁

MySQL的行锁是在引擎层实现的，MyISAM不支持行锁，所以MyISAM只能通过表锁的方式来控制并发，进而影响到业务并发度。

行锁是针对数据表中行记录的锁。两个事务同时更新一条记录，需要等待对方事务完成之后才能进行更新。

### 3.1 两阶段锁

在InnoDB事务中，行锁是在需要的时候才加上，等到事务结束时才释放。这个时两阶段锁协议。

如果事务中需要锁多个行，要把最有可能造成锁冲突，最可能影响并发度的锁尽量向后放。

### 3.3 死锁和死锁检测

![img](4d0eeec7b136371b79248a0aed005a52.jpg)

这时候，事务 A 在等待事务 B 释放 id=2 的行锁，而事务 B 在等待事务 A 释放 id=1 的行锁。 事务 A 和事务 B 在互相等待对方的资源释放，就是进入了死锁状态。当出现死锁以后，有两种策略：

- 一种策略是，直接进入等待，直到超时。这个超时时间可以通过参数 innodb_lock_wait_timeout 来设置。
- 另一种策略是，发起死锁检测，发现死锁后，主动回滚死锁链条中的某一个事务，让其他事务得以继续执行。将参数 innodb_deadlock_detect 设置为 on，表示开启这个逻辑。

Innodb默认的innodb_lock_wait_timeout 的时间为50s，如果发生死锁后，需要50s后才能退出，这个等待时间太长。如果等待时间设置的很短，就会影响正常的事务。所以一般采用第二种策略



### 3.3 行锁的分类

行锁在InnoDB中有三种：记录锁(RR\RC)、间隙锁(RR)、临键锁(RR)。

![img](e7f7ca0d3dab2f48c588d714ee3ac861.png)

在RR隔离级别下，为解决幻读的问题，引入了间隙锁。间隙锁锁住的是记录之间的空隙。临键锁是行锁+间隙锁，范围是左开右闭。

与间隙锁存在冲突关系的是，“往这个间隙中插入一个记录"。间隙锁之间不存在冲突关系。



### 3.4 加锁规则





- 原则 1：加锁的基本单位是 next-key lock。next-key lock 是前开后闭区间。

- 原则 2：查找过程中访问到的对象才会加锁。
- 优化 1：索引上的等值查询，给唯一索引加锁的时候，next-key lock 退化为行锁。
- 优化 2：索引上的等值查询，向右遍历时且最后一个值不满足等值条件的时候，next-key lock 退化为间隙锁。
- 一个 bug：唯一索引上的范围查询会访问到不满足条件的第一个值为止。



加锁规则如上，具体的场景可以参考以下

| 场景                     |      |
| :----------------------- | ---- |
| 等值查询间隙锁           |      |
| 非唯一索引等值锁         |      |
| 主键索引范围锁           |      |
| 非唯一索引范围锁         |      |
| 唯一索引范围锁bug        |      |
| 非唯一索引存在等值的情况 |      |
| limit语句加锁            |      |
| 不等号条件里的等值查询   |      |
|                          |      |

注意：lock in share mode只锁覆盖索引，for update会顺便给主键索引加上行锁。如果要用 lock in share mode 来给行加读锁避免数据被更新的话，就必须得绕过覆盖索引的优化，在查询字段中加入索引中不存在的字段。
